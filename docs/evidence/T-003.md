## 安全边界

- AgentBeacon 只把 Herdr Unix socket 作为状态来源；CLI 只用于核实版本、状态和随安装版本发布的协议 schema。
- 采样器不调用 `pane.read`、`agent.read` 或 `session.snapshot`，不输出终端正文、标题、工作目录、原生会话引用或凭据。
- 当前开发 Agent 不在 Herdr 托管 pane 内，缺少 `HERDR_ENV`、`HERDR_SOCKET_PATH` 和 `HERDR_PANE_ID`，因此没有从外部读取当前 Herdr 会话。

## 已确认协议

- Unix 使用 Unix domain socket；传输格式为一行一个 JSON（NDJSON）。请求包含 `id`、`method`、`params`，响应使用相同 `id`。
- 默认 session socket 是 `~/.config/herdr/herdr.sock`；命名 session 位于 `~/.config/herdr/sessions/<name>/herdr.sock`。Herdr pane 会注入 `HERDR_SOCKET_PATH`。
- 状态枚举与 AgentBeacon 五态一致：`idle`、`working`、`blocked`、`done`、`unknown`。
- 初始状态可由只读 `agent.list` 获取；长期变化由 `events.subscribe` 推送。
- 单 pane 状态订阅使用 `pane.agent_status_changed`，schema 要求明确的 `pane_id`；推送数据至少包含 `pane_id`、`workspace_id` 和 `agent_status`。
- 生命周期还需监听 `pane.agent_detected`、`pane.exited`、`pane.closed`，用于新增、退出和关闭时清除状态。
- Herdr 0.8.2 的全局生命周期订阅会重放保留的历史事件；实测收到已关闭 `wM:p1` 的旧 `pane_agent_detected`，直接按事件订阅该 pane 会返回 `pane_not_found`；也收到当前 `wP:p1` 的旧 release 后又收到 detected。消费者必须等待初始 reconciliation 完成，并用 `agent.get` / `agent.list` 当前状态核对新增与清除，不能把订阅流当作只含实时事件。
- 官方说明要求断线重连后重新获取快照；协议升级时先检查 server protocol，并宽容处理未知字段。
- Codex 官方 integration 只报告原生 session identity；Codex 状态仍由 Herdr screen manifest detection 判定。不能把“已安装 Codex integration”误记为结构化生命周期状态来源。

实现时的竞态处理建议留给 T-004 定案：先建立全局 pane 生命周期订阅，读取 `agent.list`，为现有 pane 建立状态订阅，再读取一次 `agent.list` 做 reconciliation；重放的生命周期事件先用 `agent.get` 核对，失效 pane 静默丢弃；重连重复该流程。

## 验证结论

- Agent 被识别及初始状态：已验证 `wP:p1`、`agy`、`idle`，`state_change_seq: 130`，`screen_detection_skipped: false`。
- `working`：已验证。
- `blocked`：已用 Codex 交互式提问 UI 验证；Agy 的同类普通提问未被 0.8.2 识别，见兼容性观察。
- `done` 与用户查看后的 `idle`：已验证。
- Agent 退出：已验证 `agent_released`，可据此立即清除该 Agent 状态。用户随后关闭了测试 pane；由于采样器当时在 release 后提前取消跟踪，没有单独记录 `pane_closed`，用户确认无需重复采样。该缺陷已修正，schema 中的 `pane.closed` 仍纳入生产客户端。
- 订阅连接中断后的完整恢复属于 T-007 发送端集成测试；T-003 已确认官方要求重连后重新获取当前快照。

## 采集进程生命周期结论

- AgentBeacon 采集/发送端是独立长驻进程，不依赖 Herdr plugin startup hook 充当进程监督器，也不需要安装插件才能读取状态。
- 启动时连接 `HERDR_SOCKET_PATH` 或按默认 session 规则解析主 API socket，校验 protocol，建立生命周期订阅，再用 `agent.list` 前后两次 reconciliation 建立每 pane 状态订阅。
- Herdr server 重启、socket 断开或订阅失败时，采集结果进入不可用状态；发送端执行有界退避重连，成功后重新订阅并获取最新快照，不重放 AgentBeacon 自身积压状态。
- 对 Receiver 的状态变化与周期心跳由同一个发送端进程负责；具体实例 ID、序列号、心跳参数和 unknown 转换由 T-004 定义。
- Linux 正式运行监督方式留给 T-012；Herdr 本身不负责保证 AgentBeacon 进程常驻。

## 真实状态样本

采样环境：Herdr 0.8.2、protocol 20、Herdr workspace `wP` 中的 `agy` Agent；采样器运行于同 workspace 的独立 shell pane。记录只含白名单字段。

| UTC 时间 | 事件 | Pane | Agent | 状态 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 05:49:22.508 | snapshot | `wP:p1` | `agy` | `idle` | 初始 reconciliation；screen detection 生效 |
| 05:49:22.715 | snapshot | `wP:p1` | `agy` | `idle` | 订阅建立后的二次 reconciliation，序列号仍为 130 |
| 05:49:32.362 | status_changed | `wP:p1` | `agy` | `working` | Agent 开始执行短任务 |
| 05:49:36.012 | status_changed | `wP:p1` | `agy` | `done` | 后台工作完成且尚未被查看 |
| 05:49:37.437 | status_changed | `wP:p1` | `agy` | `idle` | 完成结果被查看后回到可输入状态 |
| 06:00:06.274 | snapshot | `wP:p1` | `codex` | `working` | Codex 测试回合正在执行；screen detection 生效 |
| 06:00:09.726 | status_changed | `wP:p1` | `codex` | `blocked` | 显示交互式提问 UI，等待用户回答 |
| 06:00:18.783 | status_changed | `wP:p1` | `codex` | `working` | 用户回答后继续执行 |
| 06:00:27.313 | status_changed | `wP:p1` | `codex` | `idle` | 当前 tab 可见，完成后回到 idle |
| 06:02:31.555 | agent_released | `wP:p1` | `codex` | `idle` | Codex 退出，Herdr 释放该 pane 的 Agent 生命周期状态 |

实测状态顺序为 `idle → working → done → idle`，与 Herdr 0.8.2 内置说明一致。

Codex 另一次实测为 `working → blocked → working → idle → agent_released(idle)`，验证了交互式提问、回答后恢复和 Agent 退出。测试期间 pane 保持在用户当前可见 tab，因此回合结束后落到 `idle`，没有产生后台未查看语义的 `done`。

兼容性观察：Agy 普通交互式提问的实际序列为 `working → idle`，未出现 blocked。Agy 在本机由 screen manifest 检测（`screen_detection_skipped: false`）；Herdr 0.8.2 的 Agy manifest 只覆盖已知可见权限提示，不能假设任意提问 UI 都会可靠产生 blocked。第一版应把未被 Herdr 识别的等待状态视为上游能力边界，不通过读取终端正文自行猜测。
