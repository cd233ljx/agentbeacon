# Agent 驱动的项目管理

## 文档职责

- proposal.md：当前产品和架构方案。
- tasks.md：唯一任务看板，状态、依赖、验收和证据。
- decisions.md：已接受决定与待决定事项，不用聊天隐含决定。
- handoff.md：最新工作现场和下一步，供新 Agent 接续。
- evidence/：后续实测记录，文件名使用任务 ID；禁止记录凭据、终端正文和私人任务内容。
- proposal-original.md：历史附件，禁止当成当前规范。

## 用户与 Agent 分工

用户提供产品决策、设备权限、采购接线及真机观察。Agent 负责方案细化、实现、测试、缺陷修复、文档和交付步骤。遇到需用户操作的任务，给出最短步骤、预期输出和回传信息，不要求用户承担编程。

## 任务生命周期

状态：todo → doing → review → done。blocked 表示缺少明确外部条件，需记录原因和可继续的其他任务。
开始工作前写负责人；每个任务只设一个主负责人，不自动启动多个 Agent。任务较大时先拆分，保留父任务验收。

每项任务应包含：目标、范围、依赖、验收、验证证据、待解决问题。结果不符合验收则保持 doing/review，不以“代码已写完”替代完成。

## 完成标准

1. 需求及边界已实现，未决规则没有被偷偷固定。
2. 对应业务和故障测试通过；纯文档修改验证链接与一致性。
3. 涉及平台能力的结果标明实测环境；模拟器只能证明协议和逻辑。
4. 配置和文档同步，敏感值不入库。
5. tasks、decisions（有决定时）、handoff 已更新。
6. 汇报改动、证据、限制与下一步；用户实物验收未完成则标明。

## 变更与 Git

先检查现有工作区，不覆盖未提交修改。采用小范围、可审阅的变更；建立提交时在信息中引用任务 ID。不能因为用户要求 Agent 开发就默认授权推送、部署或操作手机。远程发布按用户实际授权执行。

范围变化先更新方案和决策，再同步受影响任务。确认缺失信息时只询问影响下一步的问题；不重复询问已确定的 Android 主接收端、Herdr 内监控范围或绿色常亮要求。

## 验证层次

- 静态：npm run check；当前仅检查 .mjs 语法。
- 单元：后续使用 node:test 覆盖聚合、校验、过期和顺序规则。
- 集成：回环地址模拟 WLED，覆盖成功、失败、延迟及恢复。
- 设备：Android 主平台、Windows 备用平台分别记录，不能相互替代。
- 验收：真实 Agent → 手机 → 灯，外加独立 Demo 和故障边界。

## 交接模板

日期；当前任务；变更文件；运行命令与实际结果；未验证部分；待决策/阻塞；下一项具体操作。不要写无法复核的“已全部完成”。
